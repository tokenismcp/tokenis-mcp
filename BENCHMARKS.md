# Benchmarks

Numbers below are generated by `benchmarks/bench.py` from `benchmarks/results.json`;
rerun it on your own hardware with:

```bash
python benchmarks/bench.py --sizes 10000 100000 1000000
python benchmarks/bench.py --report          # rewrite this file from results.json
```

How to read them:

- **Gateway service time** is the gateway's own work for one tool call
  (admission control, homomorphic summation, decryption, audit), measured
  without the uniform-latency padding. What a client sees is this rounded
  *up* to the latency quantum (250 ms by default; configurable), which is
  what the W6 and HTTP sections measure.
- Each sealed column's decryptor is sized to that column's own bound, so
  decryption cost depends on the data's magnitude, not on a worst case.
- The admission-control audit runs over *cells* -- groups of records no
  admissible query can tell apart -- so its cost does not grow with the
  record count (3,000 cells here for 10k to 1M records).
- Laptop measurements are sensitive to background load; the environment
  line records the load average when the run started. The results below
  come from a developer laptop that was also running other workloads, and
  across four full runs the same operations varied 2-5x. For example, one
  decryption at range 2^32 took a steady 1.9 ms on its own but 5-25 ms
  inside full runs, and loading 1M records took 50-135 s. Treat these
  numbers as orders of magnitude. `.github/workflows/benchmark.yml`
  reproduces the suite on a clean GitHub runner (run it from the Actions
  tab); its report lands in the job summary.

Measured 2026-09-24 on Apple M4 (10 cores, 16 GB), Darwin 27.0.0, Python 3.12.13; 1/5/15-minute load average at start [3.4, 7.4, 8.1].

### Uniform latency (W6), server side

800 `aggregate` calls from 32 concurrent clients, admitted and denied mixed: every call landed in latency bucket(s) [1] of 250.0 ms, at most 3.792 ms past the boundary (p99 2.782 ms).

### End to end over Streamable HTTP (authenticated, padding included)

`tokenis-mcp serve` over 100,000 records, 32 concurrent MCP clients, 800 calls (800 answered, 0 denied by policy):

- Throughput: 116.6 calls/s
- Latency seen by clients: p50 255.401 ms, p99 448.948 ms (quantum 250.0 ms). HTTP, JSON and queueing add p50 5.401 ms / p99 197.418 ms on top of the padded server time; that overhead depends on load, not on the data.
- Start-up including load and encryption: 13.05 s; restart including admission-history replay: 11.6 s
- Unauthenticated request: HTTP 401; budget persisted across restart: True; audit trail 800 entries, signed: True
